# Keys while the computer is locked

- Date: 2026-11-02
- Method: public OS documentation (Microsoft `WTSRegisterSessionNotification`,
  freedesktop `org.freedesktop.login1`, Apple notification threading), Deckly
  source inspection and Rust tests. The official application was not inspected
  for this entry.
- Hardware: none opened. No machine was locked and no input was injected.

## Decisions

Toggle: Preferences > General > Lock Screen, setting `lock_keys`, on by
default. Settings files without the field load as on.

| While locked | Actions | Why |
| --- | --- | --- |
| Blocked | Text, Hotkey, Open, Website, Multimedia | They inject input or act on the machine. Multimedia sends real key events on Windows and macOS. |
| Blocked | Every plugin action, and any unknown action | Third-party code can do anything, so plugins do not hear the press. Unknown UUIDs are treated the same: `actions::runs_while_locked` is an allow list. |
| Run | Next, Previous, Go to Page, Switch Profile, Folder, Parent Folder, Page Indicator, Brightness, Sleep, Delay | They stay inside Deckly and the device. |
| Per step | Multi Action, Switch, Random, Key Logic | Each step answers for itself. A run that passed over a step counts as cancelled: no OK mark, and a switch keeps its side. |

- A key press wakes a sleeping device and draws the held key as usual.
- The decision is made at the press and kept through its release, so a plugin
  hears the release of a press it heard, and only that. Tests:
  `a_press_held_back_stays_held_back_through_its_release`,
  `a_release_after_locking_still_reaches_a_press_heard_before`,
  `a_plugin_pressed_before_the_lock_still_hears_the_release`,
  `key_logic_holds_back_a_blocked_slot_and_its_release`.
- Sequences already running when the computer locks pass over blocked steps,
  and the action queue asks again before running. Tests:
  `a_locked_computer_passes_over_steps_that_act_on_the_machine`,
  `the_action_worker_passes_over_what_the_gate_blocks`.
- A plugin's own `openUrl` is not a key press and is not blocked. The plugin is
  a separate process that could open the URL itself, so blocking it would
  protect nothing.

## When detection fails: fail-open

If the lock screen cannot be detected, keys keep working and Preferences says
so. Failing closed would leave the keys dead for good on such a system, with
nothing that could ever open them again. Deckly is also not a security
boundary: the lock screen protects the session, and this setting only stops
Deckly from typing into it. Tests: `an_undetectable_lock_screen_leaves_keys_working`.

A watcher that loses its source after it worked keeps the last known state, so
a computer that locked stays locked to Deckly. Linux retries every 30 seconds.
Test: `a_lost_watcher_keeps_the_last_known_state`.

## Platform evidence

### Windows

- Documented: session changes reach a window registered with
  `WTSRegisterSessionNotification` as `WM_WTSSESSION_CHANGE`. `WTSSessionInfoEx`
  gives the current state.
- Observed on Windows 10 22H2 through tests: registration succeeds, the state
  of this session can be read, and session messages posted directly to the
  hidden window reach the gate. Tests: `this_session_reports_its_lock_state`,
  `the_hidden_window_passes_session_events_to_the_gate`.
- Inferred, not observed: that Windows sends these messages on a real lock.
  The documentation also warns the call can fail before Remote Desktop services
  are up; Deckly would then report the lock screen as undetected until restart.

### Linux

- Documented: desktops report the state with `SetLockedHint`, read as
  `LockedHint`. `Lock` and `Unlock` signals ask the session to lock. Signals are
  not emitted on the `session/auto` path, so Deckly uses the real path from the
  user's `Display` property.
- The documentation does not say whether `LockedHint` emits `PropertiesChanged`,
  so a change listed either with or without its value triggers a fresh read.
- Only compile-checked. `change` has tests under `cfg(test)` that were not run.
- Unknown: which lockers set `LockedHint` or react to `Lock`. A locker that does
  neither stays unseen, with keys active and no error. A `Lock` signal with no
  locker running counts as locked until `Unlock`.

### macOS

- Documented: distributed notification centers deliver on the main thread, and
  AppKit suspends delivery for inactive apps unless told otherwise. So observers
  are added on the main thread with `DeliverImmediately`.
- Undocumented API: `com.apple.screenIsLocked`, `com.apple.screenIsUnlocked` and
  the `CGSSessionScreenIsLocked` session key.
- Only compile-checked. Nothing here has run on a Mac.
- Unknown: whether switching to another user posts these notifications.

## Not known

Whether and how the official application handles the lock screen.
